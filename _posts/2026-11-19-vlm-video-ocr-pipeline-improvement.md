VLM(Vision Language Model)은 이미지와 텍스트를 함께 입력받아,  
시각 정보를 자연어로 해석하는 멀티모달 모델입니다.  
OCR에 VLM을 적용하면 Text Detection과 Text Recognition을 나누지 않고,  
이미지와 프롬프트만으로 화면의 텍스트를 직접 생성할 수 있습니다.  
이번 프로젝트에서는 이 방식을 장시간 영상의 자막 추출에 적용했습니다.

초기에는 범용 VLM을 파인튜닝하고 프롬프트를 조정하는 것이 주요 작업이라 생각했으나,  
실제 영상을 처리해 보니 모델 밖에서 다뤄야 할 문제도 많았습니다.  
결국 모델뿐 아니라 VLM 호출 전후의 처리 로직까지 함께 수정하게 됐습니다.

이 글에서는 장시간 영상 VLM OCR의 파인튜닝과 후처리 개선 과정을 정리합니다.  
LoRA 결과 재검토, 프레임 선별, 중복 처리, 검증 방식까지의 과정을 다룹니다.  
데이터셋 구축과 서빙 구성은 이전 글인  
[폐쇄망 AI Solution 서비스 구성 및 배포](/deploying-air-gapped-ai-solution-services/)에서 다뤘습니다.

> *본 글은 실제 프로젝트 경험을 기반으로 작성했으며,  
고객·도메인·데이터·시스템 정보와 운영 설정값은 일반화하거나 생략했습니다.*

## 1. 영상 OCR에서의 VLM 활용

OCR 전용 모델과 VLM OCR의 기본적인 차이는 이전 글의  
[OCR 전용 모델 vs VLM OCR](/deploying-air-gapped-ai-solution-services/#ocr-전용-모델-vs-vlm-ocr)에서 정리했습니다.  
여기서는 장시간 영상에 적용했을 때 달라지는 부분에 집중하겠습니다.

OCR 전용 모델은 이미지에서 텍스트 영역을 먼저 검출한 뒤 문자를 인식합니다.

```
이미지
  ↓
Text Detection
  ↓
Text Recognition
  ↓
문자열 + 위치 + 신뢰도
```

반면 VLM OCR은 이미지와 프롬프트를 입력해 문자열을 직접 생성할 수 있습니다.

```
이미지 + 프롬프트
        ↓
       VLM
        ↓
      문자열
```

추론 구조는 단순해졌지만, 서빙 인터페이스는 생성된 문자열만 반환했습니다.  
그래서 OCR 전용 모델에서 얻던 텍스트 위치와 신뢰도 정보는 쓸 수 없었습니다.

한 장의 이미지에서 글자를 추출하는 경우에는 큰 문제가 아닐 수 있습니다.  
하지만 영상에서 특정 자막만 추출하려면 텍스트의 위치도 중요해집니다.  
화면 안의 모든 글자를 읽는 것과 필요한 자막만 추출하는 것은 다른 문제이기 때문입니다.

영상에서는 동일한 자막이 여러 프레임 동안 유지된다는 점도 고려해야 합니다.

```
프레임 A → 자막 X
프레임 B → 자막 X
프레임 C → 자막 X
```

각 프레임의 OCR 결과는 정확하지만, 그대로 저장하면 같은 자막이 여러 번 기록됩니다.

반대로 화면을 따라 이동하는 텍스트는 프레임마다 일부 구간만 보일 수 있습니다.

```
프레임 A → ABCDEF
프레임 B → CDEFGH
프레임 C → EFGHIJ
```

이 경우 문자열은 서로 다르지만 같은 텍스트의 일부일 수 있습니다.

따라서 영상 OCR에서는 현재 프레임의 문자열 외에도,  
이전 프레임의 결과와 같은 내용인지 새로운 내용인지도 판단해야 했습니다.  
즉, 프레임 단위의 OCR 정확도와 영상 전체의 OCR 정확도는 구분해서 봐야 했습니다.

## 2. 초기 VLM OCR 파이프라인

초기 VLM OCR 구조는 비교적 단순했습니다.  
영상에서 일정 간격으로 프레임을 추출하고 VLM에 입력한 뒤,  
생성된 문자열을 분석 시스템의 OCR 결과 형식에 맞춰 전달했습니다.

```
영상
  ↓
프레임 추출
  ↓
VLM OCR
  ↓
결과 해석
  ↓
결과 전달
```

한 프레임에서 문자열을 추출하는 데에는 충분한 구조였습니다.  
하지만 장시간 영상을 처리하면서 원인이 다른 문제가 함께 나타났습니다.

| 문제 유형 | 발생 사례 | 주요 대응 영역 |
|------|------|------|
| 문자 인식 오류 | 실제 글자를 잘못 읽음 | 모델 / 파인튜닝 |
| Hallucination / 생성 오류 | 화면에 없는 문장이나 설명을 생성 | 프롬프트 / 출력 필터 |
| 대상 선택 오류 | 자막이 아닌 화면 속 텍스트를 추출 | 프레임 선별 / 규칙 기반 필터 |
| 프레임 간 중복 오류 | 동일 자막 반복, 서로 다른 자막 병합 | Deduplication |

처음에는 모두 OCR 결과가 잘못된 문제로 보였지만, 수정할 위치는 서로 달랐습니다.

모델이 글자를 잘못 읽었다면 모델이나 입력 조건을 확인해야 하고,  
화면에 없는 문장을 생성했다면 출력 검증이 필요했습니다.  
실제 텍스트를 읽었더라도 자막이 아니라면 추출 대상을 제한해야 했습니다.  
또한 각 프레임의 OCR이 정확해도 결과를 합치는 과정에서 오류가 생길 수 있었습니다.

이후에는 오류가 발견되면 먼저 어느 단계에서 발생했는지 확인하고,  
모델과 인터페이스, 후처리 로직의 수정 범위를 구분했습니다.

## 3. LoRA 파인튜닝과 결과 재검토

범용 VLM이 특정 영상 환경의 자막 형태에 더 잘 대응하도록,  
PEFT(Parameter-Efficient Fine-Tuning) 방식으로 파인튜닝을 진행했습니다.  
PEFT는 원본 가중치를 고정하고 적은 수의 추가 파라미터만 학습하는 방법입니다.

파인튜닝 데이터셋은 이전 글의  
[데이터셋 구축: 모델 보조 라벨링](/deploying-air-gapped-ai-solution-services/#1-데이터셋-구축-모델-보조-라벨링)에서 소개한 방식으로 구축했습니다.  
범용 모델의 초기 OCR 결과를 사람이 검수·수정해 정답을 만드는 방식입니다.  
여기서는 데이터셋 구축 대신 실제 파인튜닝 구현과 결과에 집중하겠습니다.

### 1. LoRA 적용

LoRA의 기본 개념 역시 이전 글의  
[LoRA 파인튜닝](/deploying-air-gapped-ai-solution-services/#2-lora-파인튜닝)에서 정리했습니다.

이번 작업에서는 PEFT 방법 중 LoRA(Low-Rank Adaptation)를 사용했습니다.  
어댑터는 Attention과 Feed-Forward 계층의 Projection Layer에 추가했습니다.  
어댑터를 적용하는 추론 경로도 구성해 같은 입력에서 적용 전후 결과를 비교했습니다.

이전 글에서는 파인튜닝 후 문자 오류율(CER)이 개선된 결과를 정리했습니다.  
하지만 입력별로 보면 개선은 대부분 일부 입력에서 과잉 생성이 줄어든 효과였습니다.  
나머지 입력은 거의 변화가 없었고, 오히려 나빠진 입력도 있었습니다.  
평가 데이터의 규모도 제한적이었습니다.  
따라서 이 결과만으로 운영 환경에서도 더 나은 성능을 낸다고 판단하지는 않았습니다.

또한 실제 영상에서 문제가 됐던 자막 외 텍스트 추출, 동일 자막 반복,  
이동하는 텍스트 등은 모델보다 프레임 선별과 후처리에서 다뤄야 할 문제였습니다.  
이러한 이유로 파인튜닝 어댑터는 운영 경로에 적용하지 않았습니다.

### 2. 어댑터가 Vision Encoder에도 삽입된 문제

파인튜닝 코드를 다시 확인하면서 예상과 다른 부분도 발견했습니다.

이전 글에서는 Vision Encoder와 Projector를 동결하고,  
Language Model에만 LoRA를 적용하는 구성을 일반적인 방식으로 소개했습니다.  
이번 학습 코드에서도 Vision Encoder의 파라미터는 학습 전에 동결했습니다.

그런데 저장된 어댑터를 보니 Vision Encoder 내부에도 LoRA 파라미터가 있었습니다.

원인은 `target_modules` 설정이었습니다.  
PEFT는 대상 모듈을 이름 목록으로 받으면,  
이름이 같거나 그 이름으로 끝나는 모든 모듈에 어댑터를 삽입합니다.  
Vision Encoder에도 같은 이름의 Projection Layer가 있어 함께 포함됐습니다.

```
Vision Encoder 원래 가중치 동결
        ↓
LoRA 대상 모듈 탐색
        ↓
같은 이름의 Vision 모듈도 대상에 포함
        ↓
새 LoRA 파라미터 삽입
        ↓
새 어댑터 파라미터는 학습 가능
```

PEFT는 어댑터를 삽입하면서 기존 가중치를 모두 동결합니다.  
따라서 Vision Encoder를 미리 동결한 것은 삽입 범위와 관계가 없었고,  
어댑터가 들어갈 위치는 `target_modules`로만 정해졌습니다.  
기존 가중치가 동결돼 있어도 그 위에 삽입된 어댑터는 학습 대상이 됩니다.

어댑터의 모듈 이름을 계층별로 집계해 보니 상당 부분이 Vision Encoder에 있었습니다.  
Language Model에만 적용하려면 이름이 아니라 계층 경로로 범위를 한정해야 했습니다.

## 4. 파인튜닝 이후에도 남은 문제

파인튜닝 이후에도 실제 영상에서는 문자 인식 오류 외의 문제가 남아 있었습니다.

VLM이 화면에 없는 내용을 생성하는 Hallucination이 있었고,  
간판이나 문서처럼 추출 대상이 아닌 실제 텍스트를 읽는 경우도 있었습니다.

동일한 자막을 여러 프레임에서 반복해서 읽는 경우도 있었습니다.  
이때 각 프레임의 OCR 결과는 정확하기 때문에 문자 인식 오류라고 보기는 어렵습니다.

따라서 이후 작업은 다음 세 부분을 중심으로 진행했습니다.

```
생성 결과 자체가 잘못됨
        → 출력 필터링
        → VLM 호출 프레임 선별

실제 텍스트지만 추출 대상이 아님
        → VLM 호출 프레임 선별
        → 규칙 기반 필터링

각 프레임의 결과는 맞지만 중복됨
        → 프레임 간 중복 처리
```

먼저 프롬프트와 VLM 출력 검증부터 수정했습니다.

## 5. 프롬프트와 Hallucination 제어

프롬프트에서는 읽을 대상뿐 아니라 제외할 대상도 함께 정의했습니다.

주요 조건은 다음과 같았습니다.

- 필요한 화면 텍스트만 추출
- 로고와 워터마크 등 고정 요소 제외
- 화면에 없는 내용 생성 금지
- 원문을 임의로 수정하거나 번역하지 않음
- OCR 결과 외의 설명문 생성 금지
- 대상 텍스트가 없으면 정해진 빈 결과 반환

하지만 프롬프트를 수정하더라도 생성 오류가 완전히 사라지지는 않았습니다.  
따라서 VLM 응답을 받은 뒤 인터페이스에서도 결과를 검사하도록 했습니다.

### 1. 프롬프트 문구를 다시 출력하는 문제

VLM이 프롬프트에 포함된 표현을 실제 OCR 결과처럼 반환하는 경우가 있었습니다.

특정 문자열을 필터에 하나씩 추가할 수도 있었지만,  
그렇게 하면 프롬프트가 바뀔 때마다 필터도 따로 수정해야 합니다.

그래서 현재 프롬프트에서 비교 대상 문자열을 생성하고,  
VLM 출력이 해당 문구와 일치하거나 일부를 그대로 담고 있는지 검사했습니다.  
프롬프트가 변경되면 비교 대상도 함께 갱신되는 방식입니다.

### 2. 생성 오류와 규칙 기반 필터의 구분

후처리에서도 모든 문자열을 같은 방식으로 제거하지 않았습니다.

설명문, 프롬프트 문구 재출력, 비정상적으로 긴 생성처럼  
VLM 응답 자체에 문제가 있는 경우에는 출력 검증 단계에서 처리했습니다.  
반면 실제 화면 텍스트지만 자막이 아닌 경우는 규칙 기반 필터에서 처리했습니다.  
필터를 구분한 이유는 잘못된 생성과 잘못된 대상 선택이 다른 문제였기 때문입니다.

다만 화면에 없는 자막 형태의 문장은 문자열만으로 정상 결과와 구분하기 어려웠습니다.  
이런 생성은 출력 필터보다 VLM 호출 프레임 선별로 줄였습니다.

프롬프트와 출력 필터로도 해결하기 어려웠던 부분은 텍스트의 위치였습니다.  
VLM이 생성한 문자열만으로는 텍스트가 화면 어디에 있었는지 판단하기 어려웠습니다.

## 6. Text Detector를 이용한 VLM 호출 프레임 선별

VLM OCR에는 OCR 전용 모델의 Text Detection 단계가 없습니다.  
그래서 프롬프트에서 자막만 추출하도록 지정해도,  
간판, 문서, 화면 UI 등의 텍스트를 읽는 경우가 있었습니다.

이러한 결과는 문자 인식 자체가 잘못된 것은 아닙니다.  
실제로 존재하는 텍스트를 정확하게 읽었지만 필요한 대상이 아니었던 것입니다.

또한 자막이 없는 프레임에서도 VLM이 텍스트를 생성하는 경우가 있었습니다.

이를 보완하기 위해 OCR 전용 모델에서 쓰이는 CRAFT Text Detector를 활용했습니다.  
다만 검출된 영역을 문자 인식 모델에 넘기는 2단계 구조로 되돌리지는 않았습니다.  
Detector 결과로 자막 형태의 텍스트가 있는 프레임을 선별한 뒤 VLM을 호출했습니다.

```
프레임
  ↓
Text Detector
  ↓
자막 후보 영역이 존재하는가?
  ├─ 아니오 → VLM 호출 생략
  └─ 예     → 원본 프레임을 VLM에 입력
```

프레임 선별에는 검출 영역의 상대 크기, 가로·세로 비율, 화면 내 위치를 사용했습니다.  
즉, Detector를 문자열 인식이 아니라 VLM 호출 여부를 판단하는 데 사용했습니다.

여기서 중요한 점은 검출 영역을 잘라 VLM에 전달하지 않았다는 것입니다.  
Detector로는 자막 후보만 확인하고, VLM에는 원본 프레임을 입력했습니다.  
주변 시각 정보는 유지하면서 불필요한 호출과 자막 없는 프레임의 생성 오류를 줄였습니다.

다만 이 방식으로 자막 외 텍스트를 완전히 제거할 수 있는 것은 아닙니다.  
자막 후보가 있는 프레임에도 로고나 간판 등이 함께 나타날 수 있기 때문입니다.  
따라서 프레임 선별 이후에도 VLM 출력에 대한 규칙 기반 필터링을 유지했습니다.

반대로 Detector가 놓친 자막은 이후 단계에서 되살릴 수 없습니다.  
그래서 선별 조건도 정답 자막과 비교해 누락이 없는지 함께 확인했습니다.

## 7. 프레임 간 중복 처리

자막을 정확하게 읽더라도 같은 자막이 여러 프레임에서 반복되는 문제는 남았습니다.

처음에는 문자열 유사도를 기준으로 중복을 제거하려 했습니다.  
하지만 실제 영상에서는 완전히 같은 문자열, 한두 글자만 다른 문자열,  
이동하며 일부가 달라지는 문자열을 한 가지 기준으로 처리하기는 어려웠습니다.

그래서 비교 방법과 시간 조건을 나누었습니다.

| 비교 방식 | 사용 목적 |
|------|------|
| Exact Match | 동일 문자열의 반복 제거 |
| Edit Distance | 몇 글자만 다른 OCR 오인식 처리 |
| String Similarity | 길이 대비 비율로 유사 문자열 비교 |

비교 방식마다 적용하는 시간 범위도 따로 두었습니다.  
유사도 비교는 가까운 시점에 등장한 결과에만 적용했습니다.  
중복으로 판단되면 먼저 기록된 결과를 남겼습니다.

시간 범위를 두지 않았을 때는 한참 뒤에 다시 나온 정상 자막까지 사라졌습니다.  
이 문제는 짧은 영상에서는 드러나지 않고 장시간 영상에서만 확인됐습니다.

### 1. 숫자가 다른 문자열

Edit Distance만 쓰면 의미가 다른 문자열을 같은 결과로 판단할 수 있습니다.  
예를 들어 다음 두 문자열은 한 글자만 다릅니다.

```
항목 A-101
항목 A-102
```

문자열 전체로는 거의 같지만 실제로는 서로 다른 결과입니다.  
그래서 문자열 안의 숫자열을 따로 추출해 비교했습니다.  
숫자 구성이 다르면 Edit Distance만으로 중복 처리하지 않도록 했습니다.

### 2. 짧은 문자열

짧은 문자열에서는 한 글자의 차이가 전체 의미에서 차지하는 비중이 큽니다.  
긴 문장과 같은 기준을 쓰면 서로 다른 짧은 자막이 하나로 처리될 수 있었습니다.  
따라서 짧은 문자열은 편집 거리와 유사도 조건을 더 보수적으로 적용했습니다.

### 3. 화면을 따라 이동하는 텍스트

화면을 따라 이동하는 텍스트는 프레임마다 일부 구간만 나타날 수 있습니다.

```
ABCDE
  CDEFG
    EFGHI
```

완전 일치만 사용하면 서로 다른 세 개의 결과가 됩니다.  
이 경우 문자열의 겹치는 구간과 시간 간격을 이용해,  
같은 문장의 일부로 판단되면 새 결과로 기록하지 않았습니다.  
조각을 이어 붙여 전체 문장을 복원하지는 않았습니다.

다만 짧은 문자열은 서로 다른 자막이 이어질 수 있어 최소 길이 조건을 함께 두었습니다.  
중복 제거에서는 유사도와 함께 등장 시점과 문자열의 특성도 확인해야 했습니다.

## 8. 검토했지만 적용하지 않은 접근

고도화 과정에서 검토한 방법을 모두 최종 코드에 남기지는 않았습니다.  
일부 영상에서는 결과가 좋아 보이는 방법도 있었습니다.  
하지만 다른 영상에서는 정상 자막이 사라지거나 새로운 오류가 생겼습니다.

### 1. 오래 유지되는 텍스트 제거

처음에는 오래 유지되는 텍스트를 로고나 고정 화면 요소로 볼 수 있다고 생각했습니다.  
하지만 실제로는 추출해야 하는 제목이나 자막도 오래 유지되는 경우가 있었습니다.  
따라서 오래 존재한다는 이유만으로 텍스트를 제거하는 방식은 적용하지 않았습니다.

### 2. 입력 영역 크롭

자막이 주로 화면의 특정 위치에 나타난다는 점을 이용해,  
해당 영역만 잘라 VLM에 입력하는 방법도 검토했습니다.

이렇게 하면 불필요한 영역은 줄지만, VLM이 참고할 주변 시각 정보도 함께 사라집니다.  
일부 입력에서는 오히려 설명형 출력이나 Hallucination이 늘었습니다.

최종적으로는 입력 영역을 제한하는 대신 Detector로 호출할 프레임을 선별하고,  
VLM에는 원본 프레임을 전달하는 방식을 선택했습니다.

### 3. 여러 필터를 동시에 강화하기

출력 필터와 중복 제거 규칙을 동시에 강화하자 특정 영상에서는 결과가 좋아졌습니다.  
하지만 다른 영상에서는 같은 문구가 반복 출력되는 Regression이 발생했습니다.

이후에는 변경 전 구조로 되돌린 뒤 변경 사항을 하나씩 다시 적용했습니다.

```
변경 사항 적용
      ↓
동일 입력으로 재실행
      ↓
추가된 결과 / 사라진 결과 비교
      ↓
다른 영상에서도 확인
      ↓
운영 적용 여부 결정
```

비교 기준으로는 장시간 영상 한 편의 정답 자막을 만들었습니다.  
정답 자막은 OCR 결과를 참고하지 않고 영상을 보며 따로 작성했습니다.  
버전마다 정답 자막이 얼마나 남았는지, 정답에 없는 출력이 늘었는지 비교했습니다.  
버전을 거치며 정답 자막이 결과에 남는 비율은 크게 높아졌습니다.

규칙을 바꿀 때는 저장해 둔 VLM 응답으로 후처리만 다시 실행했습니다.  
Greedy Decoding을 사용해 같은 입력에는 항상 같은 응답이 나왔기 때문에,  
재실행 결과를 실제 실행과 같은 조건으로 비교할 수 있었습니다.  
덕분에 장시간 영상에서도 변경의 영향을 빠르게 확인할 수 있었습니다.

이외에도 입력 이미지 확대와 맞춤법 교정을 검토했지만 적용하지 않았습니다.  
확대는 효과가 없었고, 맞춤법 교정은 원문 표기와 고유명사까지 바꿨습니다.

검증 과정에서는 지표나 결과 건수만 보고 판단하지 않았습니다.  
자막이 끊겼다 다시 나타나면 중복 제거를 풀어 주는 규칙을 시험했을 때,  
정답 기준 지표는 좋아졌지만 같은 자막이 여러 번 기록되고 있었습니다.  
그래서 늘어난 결과와 사라진 결과를 직접 확인한 뒤 적용 여부를 정했습니다.  
한 영상에서 좋아져도 다른 영상에서 정상 자막을 잃는다면 적용하기 어려웠습니다.

## 9. OCR 결과의 Timestamp 문제

OCR 문자열이 정확해도 잘못된 시점과 연결되면 최종 결과에 오류가 생깁니다.  
분석 시스템은 Frame Index와 FPS로 시간을 계산했지만,  
실제 미디어의 시간 정보는 `frame_index / fps`와 항상 일치하지 않았습니다.  
VLM OCR보다는 시간 환산 방식의 문제라 별도의 글에서 정리할 예정입니다.

## 10. 최종 운영 파이프라인

실제 영상에서 발견한 문제를 하나씩 수정해 다음과 같은 구조를 구성했습니다.

```
영상
  │
  ▼
프레임 입력
  │
  ▼
Text Detector
  │
  ├─ 자막 후보 없음 → VLM 호출 생략
  │
  └─ 자막 후보 있음
          │
          ▼
        기본 VLM
          │
          ▼
       출력 검증
   - 빈 결과
   - 설명형 출력
   - 과도한 길이
   - 프롬프트 재출력
          │
          ▼
      규칙 기반 필터
          │
          ▼
      프레임 간 비교
   - Exact Match
   - Edit Distance
   - String Similarity
   - 숫자 변화 확인
   - 이동 텍스트 처리
          │
          ▼
        결과 전달
          │
          ▼
       분석 시스템
```

최종 운영 경로에서는 파인튜닝 어댑터를 적용하지 않은 기본 VLM을 사용했습니다.  
파인튜닝의 개선은 일부 입력에 한정돼 운영 성능 향상으로 판단하기 어려웠습니다.

실제 영상에서는 모델 외에도 프레임 선택, 출력 필터링, 중복 처리가 결과를 좌우했습니다.  
따라서 최종 운영본은 기본 VLM에 이 처리 단계들을 조합해 구성했습니다.

## 마무리

이 글에서는 VLM OCR을 장시간 영상에 적용하며 확인한 문제와 개선 과정을 정리했습니다.

1. LoRA 파인튜닝의 CER 개선이 일부 입력의 과잉 생성 감소에 한정됨을 확인
2. 이름 기반 대상 지정으로 어댑터가 Vision Encoder에도 삽입됐음을 확인
3. 생성 오류는 출력 검증으로, 자막 외 텍스트는 규칙 기반 필터로 분리해 처리
4. Text Detector로 호출 프레임을 선별해 자막 없는 프레임의 생성 오류 감소
5. 비교 방식별 시간 범위와 숫자·짧은 문자열·이동 텍스트 예외로 중복 처리
6. 저장된 VLM 응답 재실행과 정답 자막 비교로 규칙 변경의 Regression 검증
7. 파인튜닝 어댑터 없이 기본 VLM과 전후 처리를 조합한 운영 구조 구성

OCR 결과가 잘못됐다고 해서 항상 모델이 글자를 잘못 읽은 것은 아니었습니다.  
생성 오류, 대상 선택 오류, 프레임 간 중복은 각각 수정할 단계가 달랐습니다.  
오류가 발생한 단계를 먼저 구분해야 수정 범위를 정할 수 있었습니다.

검증에서도 지표가 좋아졌다는 사실만으로는 판단할 수 없었습니다.  
파인튜닝의 CER 개선은 입력별로 나눠 보자 일부 입력에 한정됐고,  
한 중복 제거 규칙은 지표를 높이면서도 같은 자막을 여러 번 기록했습니다.  
변경의 효과는 입력별 결과와 실제 출력을 함께 확인한 뒤에 판단했습니다.

영상 OCR의 정확도는 모델만이 아니라 VLM 호출 전후의 처리 전체가 함께 결정합니다.
