STT(Speech-to-Text)는 오디오에 포함된 사람의 음성을 텍스트로 변환하는 기술입니다.  
이번 프로젝트에서는 [Whisper Large-v3](https://huggingface.co/openai/whisper-large-v3)로 영상 속 발화와 시간 정보를 추출했습니다.  
첫 버전에도 음성 구간 검출(VAD), 오디오 정규화, 반복 문장 제거 처리가 있었습니다.  
다만 Whisper는 오디오에 없는 말을 만들어 내는 환각(Hallucination)을 일으키기도 합니다.  
운영에서는 이런 잘못된 출력을 줄이면서 정상 발화는 보존해야 했습니다.

초기에는 VAD 기준값이나 후처리 조건을 조정하면 환각을 줄일 수 있다고 생각했으나,  
장시간 영상을 반복 분석해 보니 문제는 후처리 조건만의 것이 아니었습니다.  
모델과 라이브러리는 바꿀 수 없다는 제약도 있었습니다.

이 글에서는 Whisper STT의 환각을 줄이며 추론 인터페이스를 고도화한 과정을 정리합니다.  
추론 인터페이스는 Whisper 호출 전후의 입력 구성, 출력 검증, 결과 전달을 맡는 코드입니다.  
화면 속 자막 추출은 [VLM 기반 영상 OCR 파이프라인 개선](/vlm-video-ocr-pipeline-improvement/)에서 다뤘습니다.

> *본 글은 실제 프로젝트 경험을 기반으로 작성했으며,  
고객·도메인·데이터·시스템 정보와 운영 설정값은 일반화하거나 생략했습니다.*

## 1. STT와 Whisper

### 1. STT(Speech-to-Text)

STT는 ASR(Automatic Speech Recognition)이라고도 부릅니다.  
"오늘 오후에는 비가 내릴 예정입니다."라는 음성을 넣으면 그 문장을 텍스트로 돌려줍니다.

Whisper는 OpenAI가 공개한 음성 인식 모델로,  
음성 입력부터 텍스트 생성까지 하나의 모델로 처리합니다.  
이런 모델을 End-to-End 음성 인식 모델이라고 합니다.

### 2. Whisper의 구조

Whisper는 Transformer 기반의 Encoder-Decoder 구조입니다.  
Encoder는 오디오에서 음향 특징을 뽑아내고,  
Decoder는 그 특징을 바탕으로 텍스트를 순차적으로 생성합니다.  
이때 문장마다 시작·종료 시각을 나타내는 시간 정보(Timestamp)도 함께 생성할 수 있습니다.

원본 오디오는 먼저 Log-Mel Spectrogram으로 변환됩니다.  
이는 소리를 시간과 주파수 축의 특징으로 나타낸 입력 형태입니다.

```
오디오
  ↓
Log-Mel Spectrogram
  ↓
Encoder: 음향 특징 분석
  ↓
Decoder: 텍스트 생성
  ↓
인식 결과
```

Whisper는 음성과 단어를 1:1로 대응시키는 모델이 아니라, 텍스트를 생성하는 모델입니다.  
음향 정보가 부족해도 언어 패턴만으로 문장을 완성할 수 있어 환각이 생기기도 합니다.

### 3. Whisper Large-v3

Whisper Large-v3는 약 15.5억 개의 매개변수를 가진 Whisper 모델입니다.  
Mel Bin은 사람의 청각 특성을 반영해 주파수 영역을 나누는 단위입니다.  
이전 Large 계열보다 입력 Mel Bin이 80개에서 128개로 늘었습니다.

학습 데이터는 약 100만 시간의 약한 라벨 음성과 400만 시간의 의사 라벨 음성입니다.  
대규모 데이터 덕분에 다양한 언어와 음향 환경에 대응하지만,  
공개 모델 설명에서도 실제로 발화되지 않은 문장을 생성할 수 있다고 안내합니다.

## 2. 오디오 처리와 VAD

Whisper에 넣기 전 오디오를 어떻게 다루느냐에 따라서도 결과가 달라졌습니다.

### 1. 16kHz와 모노

Sample Rate는 1초의 오디오를 몇 개의 값으로 표현하는지를 뜻합니다.  
16kHz는 1초를 16,000개의 샘플로 표현한다는 의미입니다.  
모노(Mono)는 채널이 하나인 오디오로, 좌·우 두 채널을 쓰는 스테레오와 구분됩니다.

[FFmpeg](https://ffmpeg.org/)는 영상과 오디오를 녹화·변환·스트리밍하는 오픈소스 도구입니다.  
이번 프로젝트에서는 FFmpeg로 영상에서 오디오를 추출해 16kHz 모노로 변환했습니다.  
Whisper가 16kHz 모노 오디오를 기준으로 동작하기 때문입니다.

### 2. RMS와 오디오 정규화

RMS(Root Mean Square)는 특정 구간의 신호 세기를 나타내는 값입니다.  
RMS가 낮으면 무음이나 작은 신호일 가능성이 크지만,  
멀리서 말하거나 작게 말한 발화도 RMS가 낮게 나옵니다.

오디오 정규화(Normalization)는 신호 크기를 일정한 범위로 맞추는 과정입니다.  
작은 음성을 키우면 모델 입력에는 도움이 될 수 있지만,  
정규화된 신호로는 원본 오디오의 실제 세기를 알기 어렵습니다.

### 3. VAD(Voice Activity Detection)

VAD는 오디오에서 사람 목소리가 존재하는 구간을 찾는 기술입니다.  
VAD 모델로는 [Silero VAD](https://github.com/snakers4/silero-vad)를 사용했습니다.

VAD는 "무슨 말을 했는가?"가 아니라 "이 구간에 목소리가 있는가?"를 판단합니다.  
따라서 VAD 결과만으로는 노래와 일반 발화를 구분할 수 없습니다.

## 3. 오디오 구간화와 Long-form 추론

음성 위치를 찾은 뒤에는 어떤 길이와 단위로 오디오를 Whisper에 넘길지 정해야 했습니다.

### 1. Segment, Chunk, Overlap

이 글에서 Segment는 VAD가 찾은 하나의 음성 구간을 뜻합니다.  
Chunk는 Whisper에 한 번에 입력하는 오디오 구간입니다.  
긴 Segment는 여러 Chunk로 나눠 입력합니다.

Chunk 경계에 걸친 발화가 빠지지 않도록 인접 구간을 일부 겹쳐 분석하기도 합니다.  
이를 Overlap이라고 합니다.

```
Chunk A
|-----------------------|

                Chunk B
                |-----------------------|
                <----->
                겹치는 구간
```

Overlap은 경계의 단어 누락을 줄여 줍니다.  
대신 같은 발화가 두 Chunk에서 중복 생성될 수 있어 추가 정리가 필요합니다.

### 2. Short-form과 Long-form

Whisper는 약 30초의 오디오를 기본 처리 단위로 사용합니다.  
당시 사용한 [Transformers](https://huggingface.co/docs/transformers/model_doc/whisper) 구현은 입력 길이에 따라 처리 경로가 나뉘었습니다.  
30초 이하 입력은 짧은 오디오 처리(Short-form) 경로로,  
그보다 긴 입력은 긴 오디오 처리(Long-form) 경로로 들어갔습니다.

Whisper 추론에는 다음과 같은 환각 억제 설정이 있습니다.

| 설정 | 의미 |
|------|------|
| `no_speech_threshold` | 발화 없음 확률과 평균 로그 확률로 무음 구간을 판단하는 기준 |
| `logprob_threshold` | 생성된 토큰의 평균 로그 확률이 낮은지 확인하는 기준 |
| `compression_ratio_threshold` | 비정상적인 반복 출력을 감지하는 기준 |
| Temperature Fallback | 품질 조건을 충족하지 못한 결과를 다른 생성 조건으로 재시도하는 방식 |

Temperature는 Decoder가 다음 토큰을 고를 때의 무작위성을 조절하는 값입니다.  
이 설정들은 생성된 결과를 보고 다시 생성할지, 무음으로 건너뛸지를 판단합니다.  
생성 결과를 판단하는 설정이라, 입력의 음향 정보와 문맥이 부족한 문제는 바꾸지 못합니다.

### 3. Region

이 글에서 Region은 가까운 VAD Segment들을 원래 시간축 그대로 묶은 입력 단위입니다.  
Whisper의 용어가 아니라 긴 입력을 만들기 위해 정의한 처리 단위입니다.

```
Segment A      Segment B      Segment C
██████         ███████        █████
   \______________|____________/
                  ↓
           Long-form Region
                  ↓
                Whisper
```

## 4. Whisper에서 확인한 환각 유형

일반적인 오인식은 실제 발화를 비슷한 다른 문장으로 잘못 받아쓰는 경우입니다.  
반면 환각은 받아쓸 발화가 없는 곳에서도 문장이 생긴다는 점에서 다릅니다.

운영 데이터에서는 다음과 같은 제작문구 형태의 텍스트가 반복적으로 나타났습니다.

```
"한글자막 by ..."
"시청해 주셔서 감사합니다."
"구독과 좋아요 부탁드립니다."
```

운영 중 확인한 환각 유형은 다음과 같습니다.

| 유형 | 현상 | 구분하기 어려운 이유 |
|------|------|------|
| 비발화 구간 환각 | 무음·연주에서 문장 생성 | 음악에도 실제 가창이 존재할 수 있음 |
| 제작문구 형태 환각 | 자막·제작문구 같은 텍스트 생성 | 정상 발화와 일부 표현이 겹침 |
| 반복 환각 | 문자·단어·문장이 과도하게 반복 | 실제 반복 발화·노래 후렴 존재 |
| 의미 대체 | 실제 발화 대신 전혀 다른 자연스러운 문장 생성 | VAD와 RMS가 정상일 수 있음 |
| 다른 언어 혼입 | 대상 언어와 다른 언어의 텍스트 생성 | 다국어 모델 특성 |
| 시간 정보 이상 | 텍스트 길이와 발화 구간이 불일치 | 텍스트 자체는 맞을 수 있음 |

시간 정보 이상은 텍스트 환각은 아니지만 같은 검증 과정에서 다뤄 함께 정리했습니다.

의미 대체는 목소리가 있는 구간에서 생겨 VAD·RMS 같은 음향 신호로는 찾기 어려웠습니다.

## 5. STT 인터페이스의 고도화 과정

STT 인터페이스는 운영 오류가 확인될 때마다 원인을 추적해 수정했습니다.  
한 번의 수정은 다음 흐름으로 진행했습니다.

```
운영 오류 확인
    ↓
발생 단계와 원인 추적
    ↓
인터페이스 수정
    ↓
동일 사례 재검증
    ↓
정상 결과 회귀 확인
    ↓
적용 또는 추가 보완
```

환각을 지우면서 정상 발화도 사라지면 조건을 완화하거나 범위를 좁혔습니다.

영역별로 진행한 작업은 다음과 같습니다.

| 개선 영역 | 주요 작업 |
|------|------|
| 초기 구성 | Whisper와 VAD를 이용한 음성 구간 처리 |
| 모델 선택 | 일반 모델과 도메인 특화 모델의 추론 경로 통합 |
| 오디오 구간화 | Chunk 길이·Overlap 조정 및 중복 제거 |
| 출력 안정화 | 반복·비정상 텍스트 검증 |
| 후처리 | 전문용어·고유명사 보정과 안전장치 |
| 구조 개편 | 짧은 Chunk에서 Long-form Region 중심 처리로 변경 |
| 운영 보완 | 시간 정보 보정, 재추론, 진단 기능 추가 |

도메인 특화 모델에는 학습된 어댑터를 연결해 사용했습니다.  
어댑터는 일반 모델에 붙여 쓰는, 따로 학습된 소규모 매개변수입니다.  
분석 옵션에 따라 일반 모델이나 어댑터를 붙인 모델로 추론합니다.

이번에 쓴 어댑터는 LoRA(Low-Rank Adaptation) 방식입니다.  
LoRA 개념은 [폐쇄망 AI Solution 서비스 구성 및 배포](/deploying-air-gapped-ai-solution-services/#2-lora-파인튜닝)에서 다뤘습니다.

## 6. 변경 전 구조에서 확인한 문제

변경 전 인터페이스는 30초보다 짧은 Chunk를 중심으로 추론했습니다.  
코드에 환각 억제 설정이 있었지만 이런 입력에서는 환각이 충분히 줄지 않았습니다.  
일부 경로에서는 부족한 길이를 0으로 채우는 패딩(Padding)도 사용했습니다.  
패딩은 입력 길이를 맞추려고 신호가 없는 값을 덧붙이는 방식입니다.

인터페이스를 다시 분석해 보니 후처리 조건 외에도 구조적인 문제가 있었습니다.  
확인한 문제와 조치는 다음과 같습니다.

| 변경 전 구조 | 확인한 문제 | 조치 |
|------|------|------|
| 30초 미만 Chunk 중심 추론 | 짧은 입력의 환각이 충분히 줄지 않음 | Long-form Region으로 입력 구성 |
| 짧은 VAD Segment와 패딩 | 음향 정보가 적은 입력 구간 생성 | 가까운 Segment를 원래 시간축으로 병합 |
| 정규화된 오디오로 신호 검증 | 원본 오디오 세기를 판단하기 어려움 | 신호 검증은 원본 오디오로 분리 |
| 사용자 정의 억제 토큰 | Whisper 기본 비음성 토큰 억제를 덮어씀 | 기본 억제가 적용되도록 수정 |
| 텍스트 중심 제거 | 음향 정보·시간 정보의 오류를 구분하기 어려움 | 음향·시간 신호를 함께 보는 검증 추가 |

규칙을 더하기보다 입력 구조를 먼저 정리했습니다.

## 7. Long-form 중심으로 추론 구조 변경

짧은 Segment·Chunk 중심 구조를 Long-form Region 중심으로 바꿨습니다.

```
[변경 전]
오디오 → VAD → 짧은 Segment → Chunk + Overlap
                                    ↓
                                 Whisper
                                    ↓
                               텍스트 후처리

[변경 후]
오디오 ──────────────→ 원본 신호 검사
   │
   ↓
  VAD → 인접 Segment 병합 → Long-form Region
                                  ↓
                                정규화
                                  ↓
                                Whisper
                                  ↓
                         환각·시간 정보 검증
                                  ↓
                              텍스트 보정
```

주요 변경은 다음 세 가지입니다.

- Region 구성: 가까운 음성 구간을 묶어 Long-form 경로로 추론
- 오디오 역할 분리: 정규화는 Whisper 입력에만, 신호 검증은 원본 오디오로
- 공통 검증: 일반 모델과 도메인 특화 모델에 같은 환각·시간 정보 검증 적용

30초를 넘지 못한 Region은 앞뒤 원본 오디오를 더 포함해 Long-form 경로로 넣었습니다.  
Whisper에는 정규화한 오디오를 넣고, 소리의 세기는 원본 오디오로 확인했습니다.

---

## 8. Whisper 출력의 품질 검증

Long-form으로 바꿔도 환각이 완전히 사라지지는 않아,  
모델 출력 뒤에 음향 정보와 텍스트 특성을 함께 보는 검증 단계를 두었습니다.

```
Whisper 결과
   │
   ├─ VAD 겹침 정도
   ├─ 원본 RMS
   ├─ 음악 구간 여부
   ├─ CPS(초당 문자 수)
   ├─ 반복·압축 특성
   ├─ 제작문구 패턴
   └─ 내용 밀도
   │
   ▼
정상 / 의심 / 제거
```

CPS와 내용 밀도는 Whisper의 표준 평가 지표가 아닙니다.  
운영 오류를 가려내려고 따로 정한 진단 기준입니다.

각 신호에는 정상 발화 반례가 있어, 여러 신호를 조합해 정상·의심·제거로 나눴습니다.  
의심 결과는 바로 지우지 않고, 다른 신호를 더 보거나 재추론한 뒤 처리를 정했습니다.

### 1. VAD 겹침 정도와 RMS

Whisper가 반환한 시간 구간이 실제 VAD 음성 구간과 얼마나 겹치는지 확인했습니다.  
문장이 긴 시간을 차지하는데 그 구간에 음성이 거의 없다면 환각을 의심했습니다.  
소리의 세기는 정규화 전 원본 오디오의 RMS로 확인했습니다.

### 2. CPS(Characters Per Second)

CPS는 1초당 생성된 글자 수입니다.  
예를 들어 10초 구간에서 30자가 생성되면 CPS는 3입니다.

CPS가 비정상적으로 높다면 텍스트가 지나치게 많이 생성됐을 수도 있지만,  
시간 정보만 너무 짧게 잡힌 경우일 수도 있습니다.  
CPS가 높으면 텍스트 오류인지 시간 정보 오류인지부터 나눠 봤습니다.

### 3. 반복·압축 특성

"오 오 오 오 오..." 같은 문자 반복이나 같은 문장의 반복 생성은 환각의 단서가 됩니다.  
반복이 많은 문자열은 압축하면 크기가 크게 줄어,  
압축률로도 반복 생성을 잡아낼 수 있습니다.

다만 실제 반복 발화나 노래 후렴도 반복 특성이 높게 나옵니다.

### 4. 제작문구 패턴

"한글자막 by ...", "자막 제공 ..."은 일반 발화에서 거의 나오지 않는 문구입니다.  
이런 문구는 강한 환각 의심 신호로 사용했습니다.

반면 "감사합니다."처럼 정상 발화에도 자주 나오는 문구는 약한 의심 신호로만 썼습니다.

### 5. 내용 밀도

일부 제작문구 환각은 음성이 있는 시간에 비해 텍스트가 지나치게 짧았습니다.  
이를 확인하려고 VAD가 검출한 음성 활동 시간과 생성된 문자 수를 비교했습니다.

내용 밀도는 생성된 문자 수를 음성 활동 시간에 기대되는 문자 수로 나눈 값입니다.  
긴 음성 구간에서 짧은 제작문구 하나만 나왔다면 이 값이 낮아 비정상일 수 있습니다.  
다만 느린 가창이나 짧은 실제 발화도 이 값이 낮게 나올 수 있습니다.

### 6. 음악 구간 겹침

음악 구간은 소리 세기의 연속성과 박자 반복 같은 신호 특성으로 판정했습니다.  
연주 구간의 환각을 줄이려고 결과가 음악 구간과 얼마나 겹치는지도 봤습니다.

음악 삭제 조건은 일반 VAD 검증보다 먼저 실행됐습니다.  
음악과 많이 겹치는데 VAD가 목소리를 거의 찾지 못한 결과는 이 단계에서 지워졌습니다.

## 9. 검증 결과와 새로운 반례

### 1. 구조 개편과 규칙 보완 후의 검증 결과

오류가 났던 구간과 정상 발화 구간을 함께 확인한 결과는 다음과 같습니다.

| 검증 항목 | 당시 확인된 결과 |
|------|------|
| 알려진 음악·비발화 구간 환각 | 모두 제거 |
| 같은 비교에 포함된 정상 발화 | 모두 보존 |
| 이전에 통과하던 반복 환각 | 모두 제거 |
| 반복 검증에 포함된 정상 문장 | 모두 보존 |
| 자동 회귀 테스트 | 전부 통과 |

이 결과는 당시 고른 사례와 자동 테스트 기준이며, 전체 인식 정확도를 뜻하지는 않습니다.  
이후 장시간 영상에서 새로운 반례가 나와 보완을 이어 갔습니다.

### 2. 정상적인 짧은 발화가 삭제된 사례

짧은 텍스트를 지우는 조건을 강화하자 "네.", "예.", "왜?" 같은 단답도 함께 사라졌습니다.  
이후 짧은 텍스트는 다른 신호와 함께 보거나 의심 구간으로 분류했습니다.

### 3. 입력 구간의 시작 위치에 따른 차이

제작문구 환각을 분석하면서 확인한 사례입니다.  
같은 오디오라도 입력 구간의 시작 위치를 바꾸면 결과가 달라졌습니다.

```
입력 구간 A
|------------- 음악 ------------| 실제 발화 |
              ↓
         제작문구 환각

입력 구간 B
                          |---- 실제 발화 ----|
                                    ↓
                                 정상 텍스트
```

입력 길이를 늘리는 것만으로는 환각이 그대로인 경우가 있었지만,  
시작 위치를 실제 발화 쪽으로 옮기자 정상 문장이 나온 사례도 있었습니다.  
Decoder가 생성을 시작할 때의 음향 맥락도 결과에 영향을 줄 수 있었습니다.

### 4. 음악 억제와 노래 가사의 충돌

현장에서는 노래 영상의 가사가 거의 나오지 않는 문제가 확인됐습니다.  
이에 노래 구간을 따로 보존하는 조건을 추가했지만,  
합창 가사는 이 조건에 들지 않아 여전히 지워졌습니다.

오디오 유형별 특징과 원하는 동작은 다음과 같습니다.

| 오디오 유형 | 소리의 특징 | 원하는 동작 |
|------|------|------|
| 가창·발화 없는 배경음악·연주 | 보존할 가사나 발화가 없음 | 불필요한 텍스트 생성 억제 |
| 발화와 배경음악이 겹침 | 말소리가 음악과 함께 들림 | 실제 발화 보존 |
| 또렷한 가창(K-pop 등) | 목소리가 반주와 구분되어 들림 | 실제 가사 보존 |
| 합창 | 여러 목소리가 겹치고, 반주와 섞이기 쉬움 | 실제 가사 보존 |

합창은 여러 사람이 같은 가사를 조금씩 다른 타이밍과 음높이로 부르는 경우가 많아,  
자음이 뭉개지고 목소리가 반주와 섞여 하나의 음악처럼 들리기 쉽습니다.  
VAD가 이를 목소리로 잡지 못하면 음악 삭제 조건에 걸려 가사가 지워졌습니다.

배경음과 목소리를 나누는 음원 분리(Source Separation) 모델을 쓰는 방법이 있지만,  
폐쇄망 환경이라 새 모델을 넣으려면 이미지 보안 검수를 다시 거쳐야 했습니다.  
음원 분리는 후속 과제로 남기고, 이번에는 노래 구간 보존 조건으로 일부만 완화했습니다.  
(이미지 보안 검수 절차는 [폐쇄망 Docker 이미지 CVE 대응](/common-vulnerabilities-and-exposures/)에서 다뤘습니다.)

## 10. 운영 데이터를 바탕으로 추가 보완

장시간 영상을 계속 처리하면서 시간 정보 오류와 정상 발화 손실도 새로 발견됐습니다.

### 1. 시간 정보 보정

일부 결과는 긴 정상 문장에 지나치게 짧은 시간이 잡혀 CPS가 비정상적으로 높았습니다.

이 경우 텍스트는 그대로 두고 종료 시간을 보정했습니다.  
문장 길이로 예상 발화 시간을 계산해 종료 시간을 늘렸고,  
다음 발화와 겹치는 정도도 함께 기록했습니다.

반대로 시작 시간이 실제 음성보다 앞서는 경우도 있었습니다.  
이때는 VAD가 찾은 음성 위치를 참고해 시작 시점을 조정했습니다.

실제 발화의 시간 정보가 한참 뒤로 붙은 경우는 더 까다로웠습니다.  
처음에는 그 시각에 해당하는 말이 없어 환각으로 보고 지우는 규칙을 만들었습니다.  
하지만 해당 구간을 다시 확인해 보니 실제 발화에 시간만 늦게 붙어 있었습니다.  
이후 지우는 대신 앞쪽 빈 구간으로 재배치하도록 규칙을 고쳤습니다.

### 2. 단계별 진단 로그

최종 텍스트만 보면 문제가 어디서 발생했는지 알기 어려워,  
결과를 세 단계로 나누어 각각 기록했습니다.

```
원본 결과: Whisper 최초 출력
      ↓
검증 통과 결과: 환각·품질 검사 후
      ↓
최종 결과: 전문용어·고유명사 등 보정 후
```

각 단계에는 VAD 겹침, 원본 RMS, CPS, 반복 관련 값, 환각 의심 사유를 기록했습니다.  
이 기록으로 다음 중 어느 경우인지 구분할 수 있었습니다.

- Whisper 최초 출력부터 틀렸는지
- 품질 검증 중 정상 결과가 삭제됐는지
- 이후 텍스트 보정으로 내용이 바뀌었는지

### 3. 경계 구간 재추론

긴 구간 대부분이 음악이고 끝부분에서야 발화가 시작되면,  
Whisper가 구간 전체를 제작문구 환각 하나로 반환하기도 했습니다.  
이 결과를 통째로 지우면 끝부분의 정상 발화도 함께 사라집니다.

앞에서 본 것처럼 입력 시작 위치에 따라 결과가 달라지는 점을 이용했습니다.  
음성 경계 부근에서 시작하는 짧은 오디오를 Whisper에 다시 넣었습니다.  
이를 재추론(Re-decode)이라고 합니다.

```
환각 의심 구간
      ↓
실제 음성 경계 탐색
      ↓
경계 부근 오디오 재추론
      ↓
새 결과 품질·시간 검증
      ├─ 불안정: 사용하지 않음
      └─ 조건 충족: 누락 발화 복구
```

재추론도 항상 맞지는 않아 원래 결과보다 더 틀린 문장이나 새 반복 환각이 나오기도 했습니다.  
결국 모든 의심 구간이 아니라 경계 손실이 예상되는 상황에만 제한적으로 사용했습니다.

## 11. STT 모델 밖에서 발생한 시간 정보 문제

STT 결과가 정확해도 결과를 전달하는 단계에서 시간 정보가 틀어질 수 있었습니다.

```
Whisper → 품질 검증 → 결과 전달 → 저장·검색 → 영상 재생 화면
```

FPS(Frames Per Second)는 영상 1초에 포함된 프레임 수입니다.  
예를 들어 30FPS 영상은 1초에 30개 프레임으로 구성됩니다.  
메타데이터는 FPS·길이·해상도처럼 영상 파일을 설명하는 정보입니다.  
결과 전달 과정에서는 시작·종료 시간 외에 이 메타데이터도 함께 쓰입니다.

변경 전에는 결과 전달 단계에서 FFmpeg로 영상을 직접 읽어 길이를 쟀습니다.  
긴 영상에서는 이 작업이 시간 제한에 걸려 실제와 다른 기본 FPS가 전달됐습니다.  
이 값이 같은 영상의 메타데이터를 덮어써,  
프레임 기준으로 시각을 환산하는 다른 분석 결과가 틀어졌습니다.

이를 [ffprobe](https://ffmpeg.org/ffprobe.html) 기반 방식으로 바꿨습니다.  
ffprobe는 FFmpeg에 함께 들어 있는 영상 정보 조회 도구입니다.  
파일을 재생하거나 변환하지 않고 FPS·길이·해상도 같은 정보만 읽어 옵니다.

```
[변경 전]
영상 → FFmpeg로 영상 읽기
           ├─ 완료: 실제 메타데이터
           └─ 시간 초과: 기본 FPS 가정

[변경 후]
영상 → ffprobe → 실제 FPS·길이
```

## 12. 검토했지만 그대로 적용하지 않은 접근

일부 사례에서 효과가 있어도 정상 발화를 훼손하는 방법은 범위를 줄이거나 보류했습니다.  
검토한 방법과 판단은 다음과 같습니다.

| 접근 | 기대 효과 | 확인한 문제 | 판단 |
|------|------|------|------|
| 특정 문장 일괄 제거 | 알려진 환각 제거 | 정상 발화와 표현 중복 | 강한 제작문구 패턴에 한정 |
| 음악 구간 선제 제거 | 연주 구간 환각 감소 | 실제 가사·합창 누락 | 노래 구간 보존 조건 추가 |
| 음원 분리 모델 추가 | 배경음을 걸러 가창만 인식 | 새 모델 반입과 이미지 보안 재검수 필요 | 보류 |
| 짧은 문장 일괄 제거 | 짧은 이상 출력 감소 | 정상 단답 발화 손실 | 다른 신호와 함께 판단 |
| 높은 CPS 결과 일괄 제거 | 비정상 출력 제거 | 텍스트는 정상이고 시간만 틀린 경우 존재 | 시간 정보 보정 우선 |
| 별도 언어 판별 | 대상 언어 외 출력 제거 | 정상적인 짧은 발화를 다른 언어로 오판 | 판별 결과만으로는 지우지 않음 |
| 모든 의심 구간 재추론 | 누락 발화 복구 | 새로운 환각 발생 가능 | 경계 구간으로 범위 제한 |

## 마무리

이 글에서는 Whisper STT 추론 인터페이스를 고도화하며 확인한 내용을 정리했습니다.

1. 환각 억제 설정만으로는 짧은 Chunk 입력의 환각이 충분히 줄지 않음을 확인
2. 가까운 VAD Segment를 Long-form Region으로 묶어 입력의 음향 정보와 문맥을 확보
3. VAD·RMS·CPS·반복·압축 특성 중 어느 하나만으로는 환각을 판단할 수 없음을 확인
4. 환각처럼 보인 문장 중 일부가 시간 정보 오류임을 확인해 삭제 대신 보정·재배치
5. 재추론은 범위가 넓으면 새 환각을 만들어 경계 손실이 예상되는 구간으로 제한
6. 영상 메타데이터 조회 방식이 같은 영상의 다른 분석 결과 시각에도 영향을 줌을 확인

핵심 제약은 모델과 라이브러리를 바꿀 수 없다는 점이었습니다.  
이 범위 안에서는 합창처럼 반주와 섞인 가창을 구분하는 문제가 남았습니다.

환각을 지우는 규칙은 정상 발화까지 함께 지울 수 있습니다.  
변경마다 환각이 줄었는지와 정상 발화가 남았는지를 함께 확인했습니다.

STT 품질은 모델만이 아니라 입력 구성부터 결과 전달까지의 처리 전체가 결정합니다.
